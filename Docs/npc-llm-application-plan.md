# NPC LLM 적용 방안과 구현 계획

작성·공식 자료 확인일: 2026-10-12. 사용자 우선순위는 **지연과 정확성**이다. 사용자는 **A+C를 먼저 구현하고 B를 확장 목표로 삼는 방향**을 확정했다. 테스트 Android 기기·RAM과 모델/실행 도구는 미확정이며 모델 추론·Android 빌드 성능은 아직 측정하지 않았다. 실행 도구·모델 비교와 일정/목표 수치는 제안이며 설치·추론 구현 완료를 의미하지 않는다.

기준 계약은 [공통 데이터 규약 v1](npc-interaction-contract.md)이다. 모든 도깨비가 모델 하나를 공유하고, 게임이 반응 분기·상태 효과·감정·동작·후속 선택지를 결정한다. 모델은 개별 특성·관리 횟수·오염도·최근 컨텍스트와 반응 계획을 받아 짧은 한국어 대사만 생성한다. 서버 추론을 기본 경로로 포함하지 않는다.

## 추천 방향과 두 가지 선택 축

1. **실행 도구**: LLMUnity의 로컬 CPU 경로로 최소 연결을 먼저 검증한다. 품질이 통과하는 모델의 CPU 지연/게임 부하가 목표를 만족하지 못하면 LiteRT-LM Android 연결을 짧은 비교 실험으로 검토한다. 현재 도구가 실제 기기에서 충족한다고 단정하지 않는다.
2. **반응 생성 방식(사용자 결정)**: **A(즉석 생성)+C(반응 틀·예시 기반 제한 생성)**를 먼저 구현·평가하고, **B(상황에 맞는 사전 생성 후보 우선 + 제한 시간 내 즉석 생성 + 기본 반응)**로 확장한다. 모델 입력에는 게임이 작성한 반응 의도·사실·짧은 예시를 넣어 생성 범위를 제한한다.

실행 도구와 생성 방식은 독립된 선택이다. 엔진을 바꾸어도 사전 생성·검증·실패 처리 정책은 공통 계약 위에서 재사용한다. 모델 선택은 이름·일반 벤치마크보다 실제 한국어 NPC 평가에서 **제시간에 사용 가능한 생성 반응 비율**로 결정한다.

## 실행 경로 비교

| 경로 | 구현할 내용 | 지연 측면 | 정확성 측면 | 채택 조건 |
| --- | --- | --- | --- | --- |
| LLMUnity / LlamaLib / GGUF | 공통 인터페이스 어댑터, 단일 모델 수명, 준비·취소 연결 | Unity 연결 작업을 줄이는 출발점. Android CPU 지연·발열을 실측 | 채팅 템플릿·컨텍스트 초기화·모델/양자화 검증 필요 | 실제 기기에서 사용 가능한 반응 비율·프레임·메모리 충족 |
| LiteRT-LM / Android 네이티브 | Kotlin AAR·Unity 연결, Engine/Conversation 수명, 콜백·취소·모델 파일 연결 | CPU/GPU/NPU 선택지가 있으나 기기·모델별 지원과 게임 자원 경쟁을 확인 | 변환된 모델·템플릿·출력 동등성 확인. 엔진 변경이 의미 정확성을 보장하지 않음 | CPU 경로의 실패 원인이 추론 비용이고 추가 연결 비용보다 실측 개선이 큼 |

LLMUnity 공식 문서는 Android IL2CPP·ARM64, 모델 준비·warmup·취소·대화 기록 제어를 제공한다. 프로젝트는 Unity 6000.3.23f1이고 Android 설정은 현재 IL2CPP·ARM64이다. 패키지는 아직 추가되지 않았으며 설정의 존재가 Android 빌드 검증 완료를 뜻하지 않는다. [LLMUnity 문서](https://github.com/undreamai/LLMUnity)

확인한 LLMUnity v3.0.3 소스는 LlamaLib v2.0.5를 사용하며, 그 릴리스에는 Android Vulkan 지원 되돌리기가 기록되어 있다. llama.cpp 자체의 GPU 지원을 LLMUnity 기본 Android GPU 지원으로 해석하지 않는다. CPU 경로를 기준선으로 삼고 설치 시 버전·네이티브 라이브러리를 다시 고정·확인한다. [연결 버전 소스](https://github.com/undreamai/LLMUnity/blob/main/Runtime/LLMUnitySetup.cs), [LlamaLib 릴리스](https://github.com/undreamai/LlamaLib/releases/tag/v2.0.5)

LiteRT-LM은 Android Kotlin API와 CPU/GPU/NPU 경로를 제공한다. GPU는 네이티브 라이브러리 선언, NPU는 대응 모델·라이브러리·지원 기기 검토가 필요하다. 백그라운드에서 엔진 초기화를 처리하고 초기화·실패 시 UI를 막지 않는다. 공개 벤치마크는 우리 Unity 게임의 응답 시간으로 사용하지 않는다. [Kotlin 시작 안내](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/api/kotlin/getting_started.md), [지원 경로와 공개 측정](https://developers.google.com/edge/litert-lm/overview)

확인한 v0.18.0 `Conversation` 구현에서 Flow 수집 취소와 네이티브 `cancelProcess()`는 별도다. Unity 연결은 실제 취소 호출을 명시적으로 연결하고, 취소된 대화 상태의 재사용 여부를 검증한다. 다른 NPC에 같은 가변 대화를 넘기지 않는다. [v0.18.0 Conversation 소스](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/kotlin/java/com/google/ai/edge/litertlm/Conversation.kt)

기존 MediaPipe LLM Inference Android API는 maintenance-only이며 공식 문서는 LiteRT-LM으로 이동을 권장한다. 새 네이티브 경로는 이전 MediaPipe API 대신 LiteRT-LM을 검토한다. [Google의 이관 안내](https://developers.google.com/edge/mediapipe/solutions/genai/llm_inference/android)

## 모델 비교의 첫 범위

첫 비교는 Qwen3-0.6B와 Qwen3-1.7B의 지시형 모델을 양자화한 로컬 파일로 한다. 작은 후보와 품질 비교 후보를 같은 NPC 입력·출력 제한으로 평가한다. 한국어를 포함한 언어 지원은 후보 선정 근거이며 우리 캐릭터의 정확성 보장은 아니다. [Qwen 공식 설명](https://qwenlm.github.io/blog/qwen3/), [0.6B 모델 카드](https://huggingface.co/Qwen/Qwen3-0.6B), [1.7B 모델 카드](https://huggingface.co/Qwen/Qwen3-1.7B)

- 초기는 동일한 4-bit 계열로 비교하고, 품질 실패가 보이면 후보 하나를 더 높은 정밀도와 비교한다. 파일 크기를 총 RAM 사용량으로 간주하지 않는다. KV 캐시·중간 버퍼·Unity 메모리를 함께 측정한다.
- non-thinking 템플릿으로 긴 추론 출력을 끈다. `/no_think` 문자열만 붙였다고 hard switch가 적용됐다고 가정하지 않고 실제 GGUF/엔진의 템플릿과 출력 토큰을 확인한다. [모델 카드의 모드 전환](https://huggingface.co/Qwen/Qwen3-0.6B)
- 출력은 한 줄의 짧은 대사로 제한한다. 토큰 상한과 v1의 160 UTF-16 길이 제한은 별도로 관리한다. 토큰 상한에서 문장이 끊기면 길이만 잘라 성공시키지 않고 부적합 결과로 처리한다.
- 이 후보가 기준을 못 맞추면 한국어 품질이 확인된 다른 소형 모델을 추가한다. 최신 세대 여부보다 해당 런타임의 아키텍처·양자화 지원과 재현성을 우선한다. 공식 모델의 revision·변환 파일 SHA-256·라이선스·템플릿·샘플링 설정을 기록한다. 다운로드/변환은 아직 하지 않았다.
- Gemma 계열을 추가할 때 크기별 실제 언어 지원을 따로 확인한다. 모델 계열 전체의 다국어 설명을 모든 소형 모델의 한국어 품질로 일반화하지 않는다.

## 생성 방식별 구현 계획

### A. 입력마다 즉석 생성

`게임 판정 → 효과 적용 후 스냅샷/계획 → 짧은 프롬프트 → 로컬 생성 → 검증 → 최종 응답`

- 가장 작은 기준 구현이다. `NpcPromptBuilder`, `NpcOutputValidator`, 실제 `INpcReactionGenerator` 어댑터와 요청 수명 서비스부터 만든다. 이름은 설계상 역할이며 현재 구현된 클래스가 아니다.
- 게임이 고른 분기·반응 의도·확정 사실만 전달하고 숫자 계산·새 이벤트·관계 변화·후속 행동 생성을 요구하지 않는다. `null` 관리 횟수/오염도는 알 수 없다고 전달한다.
- 고정 지시와 동적 컨텍스트를 분리하고 한국어 예시를 최소 개수로 제공한다. 채팅 기록을 무한히 누적하지 않고 매 요청의 게임 스냅샷을 사용한다.
- 동시 추론은 초기 1개로 제한하고 짧은 대기열·준비 상태·취소·전체 deadline을 상위 서비스가 관리한다. 완성 전 토큰을 그대로 보여주지 않고 검증된 한 줄만 표시한다.
- 장점: 현재 상태를 직접 반영하기 쉽고 기준 지연/품질 측정이 단순하다. 약점: 매 입력에 모델 준비·대기·prefill·decode가 필요하며 가장 느린 요청이 UI 만족도를 떨어뜨릴 수 있다.
- 검증: cold/warm 요청, 연속 입력, NPC 교체·취소, 모델 오류와 전체 지연·의미 정확성. 이 방식이 통과하면 작은 범위의 첫 통합으로 사용한다.

### B. 사전 생성 후보 우선 + 즉석 생성

`게임이 현재 출력 계획 확정 → 정확히 맞는 준비 대사 조회 → 있으면 현재 요청에 연결 → 없으면 예산 내 생성 → 실패 시 기본 반응`

- A 위에 `NpcReactionCache`, 입력 fingerprint, 유효 조건 검사와 낮은 우선순위 사전 생성 스케줄을 추가한다.
- 캐시는 이전 `NpcInteractionResponse`를 저장하지 않는다. **검증한 대사와 적용 조건**을 저장하고 사용할 때 현재 RequestId·SessionId·InteractionId·StateVersion으로 새 결과를 구성한다.
- 초기 키는 `NpcId`, 특성/프로필 revision, 행동·분기·의도·확정 사실, 생성에 사용한 관리 횟수/오염도/최근 기록, 모델·프롬프트·검증 정책 revision의 fingerprint다. 표시 이름·언어 등 프롬프트에 들어가는 모든 의미 입력을 포함한다. 모호한 유사도 검색으로 다른 상태 대사를 가져오지 않는다.
- fingerprint와 프롬프트는 한 상태 버전에서 원자적으로 캡처한 **동일 스냅샷·출력 계획**으로 계산한다. 게임 상태를 각각 다시 조회해 서로 다른 시점의 관리 횟수·오염도·최근 기록이 섞이지 않게 한다.
- 단순 증가하는 `StateVersion`은 응답 적용 검사에는 사용하지만 캐시의 유일 키로 삼지 않는다. 변화 내용이 생성 입력 fingerprint와 다르면 무효화하고, 동일 의미라도 세션/활성 요청 검사와 만료 조건을 다시 확인한다.
- 관리처럼 효과가 있는 입력은 선택 전과 후 상태가 다르다. 초기 사전 생성은 상태를 바꾸지 않는 행동과 이미 확정된 상태를 우선한다. 관리 후 반응을 미리 준비하려면 부작용 없는 트리 미리보기로 예상 결과를 만들고, 실제 효과 적용 후 계획/fingerprint가 일치할 때만 사용한다. 미리보기 없이 모든 입력이 cache hit한다고 가정하지 않는다.
- 활성 사용자의 요청을 사전 생성보다 우선한다. 네이티브 취소가 즉시 끝나지 않을 수 있어 중단 지연도 측정한다. 전투/탭 전환 등 화면 부하·백그라운드·지속 발열 시 사전 생성량을 줄인다.
- 장점: 준비 후보가 맞으면 사용자 대기 경로에서 추론을 제거한다. 약점: miss와 최초 진입은 여전히 생성이 필요하며 잘못된 재사용은 정확성을 해친다. hit/miss·기기 부하를 분리 측정한다.
- 추천: A의 실제 정확성·속도 결과를 확인한 뒤 주 적용 방식으로 도입한다. 캐시가 모델 품질을 높인다고 주장하지 않는다.

### C. 게임이 작성한 반응 틀과 예시로 표현 생성 제한

`출력 분기 → 작성한 반응 의도·사실·짧은 예시 → 모델의 표현 변형 → 검증`

- A 또는 B와 함께 적용하는 정확성 강화 방식이다. 출력 트리 각 분기에 전달할 사실·말투 규칙·금지할 주장·기본 대사를 작성하고, 최소한의 자연스러운 한국어 예시를 준비한다.
- 초기에는 상태 수치를 직접 계산/설명하게 하지 않고 게임이 이미 정한 사실을 표현하게 한다. 숫자·아이템 지급·미발생 사건을 임의 추가하지 않도록 입력 범위를 줄인다.
- 비용이 작은 검사는 길이·제어 문자·추론 태그·언어 혼합·금지 주장 등이다. 문법(grammar/JSON) 제약은 형태를 제한할 뿐 사실 일치를 보장하지 않는다. 키워드 검사로 반어·부정·모든 의미 오류를 완전히 검증할 수 있다고 가정하지 않는다.
- 정확성을 반드시 보장해야 하는 지급/관리 결과 안내는 게임이 작성한 고정 문장이나 UI로 표시하고, 모델 대사는 감사·장난·기분 표현에 집중한다. 중요한 사실은 SLM의 설명에 의존하지 않는다.
- 실시간 2차 LLM 판정·여러 번 재생성은 초기 경로에 넣지 않는다. 부적합하면 바로 같은 분기의 기본 반응으로 끝낸다. 정밀 의미 평가는 사전 테스트와 사람 검토에서 한다.
- 장점: 생성해야 할 의미를 줄이고 기본 반응과 일관성을 유지한다. 약점: 표현 다양성이 줄 수 있고 새로운 문장의 의미 정확성이 자동 보장되지는 않는다.
- 모델 출력의 사실 정확성을 완전히 고정해야 한다면 최종 대사를 승인된 목록에서 선택/조립하는 별도 모드가 필요하다. 이는 열린 문장 생성과 다른 제품 선택이며 다양성 요구와 함께 논의한다.

## 공통 구현과 기존 규약 연결

| 책임 | 계획 | 기존 계약과 연결 |
| --- | --- | --- |
| 상태/입출력 트리 | 입력 재검증·효과 1회·상태 버전·현재 반응 계획 | `NpcInteractionSelection`, `NpcContextSnapshot`, `NpcResponsePlan` |
| 프롬프트/컨텍스트 | 고정 지시 + 단일 NPC의 필요한 의미 입력, 모델 채팅 템플릿 적용 | `NpcGenerationRequest` |
| 공유 요청 관리 | ready 상태, 실행 1개·작은 대기열, 시간 예산·취소·최종 확정 1회 | `INpcReactionGenerator`, `NpcGenerationStatus` |
| 엔진 어댑터 | LLMUnity 또는 LiteRT-LM 실행/취소/오류를 공통 결과로 변환 | `NpcGenerationResult` |
| 준비 대사 | fingerprint·유효 조건·버전·중복/최근 사용 관리 | 생성 결과를 현재 요청 ID로 재구성 |
| 출력 검증/표시 | 형식·선택한 분기 검사, stale/취소 차단, 메인 스레드 최종 표시 | `NpcInteractionResponse.TryResolve`와 호출 측 완료 잠금 |
| 측정 | 준비/대기/prefill/첫 토큰/완성/검증/표시 단계 기록 | 통계는 계약 밖의 진단 데이터 |

현재 `NpcReactionSource`는 Generated/Fallback만 있으므로 사전 생성 hit는 내부 진단으로 구분한다. 성공한 준비 대사는 새 요청에 연결한 Generated 결과로 처리할 수 있다. 추가 노출이 필요할 때만 규약을 확장한다. 게임 계약이 Unity·추론 패키지에 의존하지 않도록 실제 어댑터를 분리된 런타임 계층/어셈블리에 둔다.

공유 모델 가중치와 NPC별 상태는 분리한다. 다른 NPC의 chat history·KV 의미 상태를 재사용하지 않는다. 준비 후보가 invalid/stale이면 같은 대사를 반복 사용하지 않고 무효화한다. 모델 교체·프롬프트 수정 시 캐시를 비운다.

## 지연과 정확성의 평가 기준

### 지연

전체 표시 지연은 **접수/게임 판정 + 모델 준비/대기 + prefill + decode + 검증 + 최종 표시**다. 첫 토큰 시간과 완성 반응 시간은 따로 기록한다. 서비스 budget은 현재 v1처럼 서비스 접수부터 계산하며 전체 체감 시간도 별도 측정한다.

- p50/p95/p99 완성 표시 지연, deadline 초과율, cold/warm 초기화 시간.
- 완료한 생성만 골라 지연 통계를 내지 않고 timeout·취소·대기열 거절 수와 관측 중단 여부를 함께 보고한다. 개발용 품질 시험에서는 늦은 생성도 표시하지 않은 채 분석할 수 있으나 실제 사용자 경로에서 취소 뒤 계속 추론하도록 요구하지 않는다.
- cache hit/miss 별 지연·준비 후보 적중률·무효화율, 대체 반응 원인별 비율.
- peak memory, 게임 프레임 시간, 취소 후 실제 추론 종료까지의 시간, 15~20분 지속 부하에서 지연 변화.
- 모두 기본 대사로 처리해 표시가 빠른 경우도 별도로 기록한다. 이것을 모델 지연 개선으로 보고하지 않는다.

### 정확성

| 축 | 통과 판단 |
| --- | --- |
| 게임 결과/분기 | 실제 효과 적용 여부·반응 의도와 모순되거나 허용하지 않은 결과를 주장하지 않음 |
| 상태·최근 컨텍스트 | 관리 횟수·오염도·unknown·최근 기록을 잘못 설명하지 않음 |
| 개체 일치 | 다른 NPC 이름/특성/최근 기록/세션 정보가 섞이지 않음 |
| 캐릭터·한국어 | 지정한 말투/성격을 지키고 자연스러운 짧은 한국어로 표현함 |
| 형식 | 한 줄·길이 제한·추론 태그 없음·정상 종료 |

핵심 선택 지표는 다음이다.

`사용 가능한 생성 반응 비율 = 제한 시간 안에 형식·의미를 통과한 생성 반응을 표시한 상호작용 수 / 평가 대상으로 접수한 상호작용 수`

준비 대사도 생성 반응으로 포함하되 즉석/준비를 나눈다. 기본 반응·모델 미준비·cache miss 후 실패를 분모에서 숨기지 않는다. 사용자 취소/대상 전환은 별도 집계하며 성공 비율을 좋게 만들기 위해 제거하지 않는다. 생성 후보의 필터 전 의미 오류율, 필터 후 표시 대사의 오류율, 의미 필터 오검출율과 반복률도 기록한다.

승인된 고정 문장을 조회한 경로는 새 모델 생성으로 집계하지 않고 `approved`로 분리한다. 추론 엔진의 KV/접두사 캐시는 입력 처리 비용을 줄이는 장치이며 완성 대사를 조회하는 이 계획의 대사 캐시와 구분한다.

초기 제안 목표는 첫 시각 반응 100ms 이내, 최종 대사/기본 반응 p95 1초 이내, 생성 후보 의미 통과율 95% 이상, 사용할 수 있는 생성 반응 비율 80% 이상이다. 수치는 **제품/시험 목표 제안**이며 실측·사용자 확정값이 아니다. 식별/버전·효과/표시 중복 관련 테스트는 전부 통과해야 한다. 의미 정확성 95% 목표를 상태 변경·요청 격리의 5% 오류 허용으로 해석하지 않는다.

## 비교 실험과 10월 30일 목표

1. **10/12–14: 재현 가능한 후보 검증 준비**. 같은 게임 입력 fixture, 모델/파일/템플릿 revision, 단계별 시간 측정과 결과 rubric을 만든다. 테스트 기기가 정해지기 전에는 데스크톱에서 형식·한국어 품질만 탐색하고 Android 속도로 보고하지 않는다. 기기 확보가 늦으면 기존 실기기 확인 일정도 다시 평가한다.
2. **10/15–18: A + C 기준 구현과 모의 전체 연결**. 실제 어댑터 작업과 프레임워크/화면 작업을 병행한다. 60개 상태 조합을 각각 3회 생성해 두 모델의 첫 비교를 한다. 0/null/경계 상태, 관리 성공/불필요 분기, 상반된 특성·최근 기록, NPC 전환을 포함한다. 이는 평가 fixture이며 게임 트리 콘텐츠 확정과 구분한다.
3. **10/19–21: 실제 Android 전체 연결과 경로 선택**. 품질을 통과한 후보로 게임과 함께 cold/warm 지연·메모리·취소를 측정한다. CPU가 실패하면 짧은 LiteRT-LM 비교를 하되 가속기 변경과 모델/양자화 변경의 효과를 구분한다. 비교에 같은 가중치를 쓸 수 없다면 엔진 차이만으로 결과를 해석하지 않는다.
4. **10/22–25: B 도입과 검증 확대**. 정확한 fingerprint 기반 준비 후보와 낮은 우선순위 생성을 추가한다. 최소 120개 별도 평가 조합·3회 반복으로 품질·반복률을 검토하고, 혼합 hit/miss와 지속 부하를 실제 기기에서 측정한다. 생성 후보 준비율이 낮으면 작은 모델로 무조건 낮추지 말고 사실 범위·프롬프트·출력 길이·생성 시점을 함께 조정한다.
5. **10/26–27: 완료 후보**. 모델·프롬프트·검증 정책을 고정하고 잘못된 cache 재사용·취소·앱 복귀·모델 미준비·효과/표시 중복을 검증한다.
6. **10/28–30: 최종 회귀·수정**. 새 추론 도구/대규모 학습을 추가하지 않고 최소 완성 범위를 안정화한다.

RAG·벡터 검색·도구 호출·장기 자유 대화·파인튜닝은 초기 필수 경로에 넣지 않는다. 제한된 입력과 구조화된 게임 상태는 정확한 조회로 전달할 수 있다. 반복된 캐릭터/한국어 오류가 프롬프트와 반응 범위 조정으로 해결되지 않으면 학습 데이터·LoRA를 후속으로 검토하되 30일 완료의 선행 조건으로 삼지 않는다.

## 현재 확인한 것과 남은 확인

- 확인: 프로젝트 설정·v1 계약·공식 도구 문서/릴리스/소스·모델 카드 비교. 생성 방법·지표·구현 단계의 설계.
- 미실행: 패키지 설치·모델 다운로드/변환·Unity 빌드·모델 품질 시험·Android 추론/부하 측정.
- 미확정: 최소 지원 기기/RAM, 실제 모델/양자화·패키지 버전, 최종 budget과 목표 수치, 입출력 콘텐츠·캐릭터 표현 범위.
- 생성 방식은 **A+C 구현·검증 → B로 확장**으로 확정했다. 실행 도구의 추천 후보는 LLMUnity CPU 기준선과 필요한 경우의 LiteRT-LM 대체 비교이며, 최종 도구/모델 채택은 지연과 정확성을 함께 측정한 결과로 결정한다.
