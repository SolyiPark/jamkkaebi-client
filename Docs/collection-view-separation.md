# 도감 기능과 표시 계층 분리

2026-10-28. 브랜치 `refactor/collection-view-separation`. `19d8f70`의 필수 CanvasRenderer 수정 위에서 진행한 첫 구조 개편이다.

## 먼저 쉽게 이해하기

이번 개편의 목적은 **도감의 겉모습을 바꿀 때 수집 규칙과 화면 이동 코드까지 함께 뜯어고치는 일을 줄이는 것**이다.

이전에는 한 담당자가 두 종류의 일을 모두 했다. “금관을 복원했는지 확인하고, 상세를 열고, 신규 표시를 지우는 일”과 “금관 카드를 어느 위치에 어떤 색과 크기로 만드는 일”이다. 그 담당자가 `CollectionPresenter`였다. 기능 코드 사이에 좌표와 색상, 버튼 생성 코드가 섞여 있어서 화면을 크게 바꾸면 기능 코드도 건드리기 쉬웠다.

이제는 다음과 같이 역할을 나눴다.

| 비유 | 코드 | 하는 일 |
| --- | --- | --- |
| 원본 수집 장부 | `CollectionProgress` | 어떤 유물을 복원했는지, 무엇을 아직 읽지 않았는지 기록한다. 건물 해금 같은 기존 수집 규칙도 여기서 판정한다. |
| 처리 담당자 | `CollectionPresenter` | 사용자 요청이 가능한지 확인하고, 어느 화면을 보여줄지 결정한다. 원본 장부 변경도 이 흐름에서 요청한다. |
| 장부에서 복사한 안내지 | `CollectionViewData` | 지금 보여줄 수집 수·잠금·신규·해금 상태와 선택 항목을 담는다. 원본 장부를 바꾸는 기능은 담지 않는다. |
| 화면 담당자의 공통 약속 | `CollectionView` | 새 화면이 어떤 방식으로 데이터를 받고, 버튼 입력을 어떻게 알릴지 정한다. |
| 지금 쓰는 화면 담당자 | `CollectionDefaultView` | 기존 도감의 실제 버튼·글자·그림을 만들고 배치한다. |

`CollectionView`와 `CollectionDefaultView`는 같은 뜻이 아니다. 전자는 **화면 담당자가 지켜야 할 사용법**, 후자는 **그 사용법을 지키면서 현재 디자인을 그리는 실제 코드**다. 새 디자인은 사용법을 유지하면서 만드는 방법을 바꾸면 된다.

## 유물 카드를 누르면 실제로 무슨 일이 생길까?

복원한 삼국 금관 카드를 누르는 예를 보면 다음 순서다.

1. **View가 버튼 입력을 받는다.** “삼국 금관을 보고 싶다”는 요청을 `samguk-crown`이라는 ID와 함께 알린다.
2. **Presenter가 요청을 확인한다.** 카탈로그에 그 ID가 있는지, 원본 기록에서 정말 복원한 유물인지 검사한다.
3. **Presenter가 화면 상태와 기록을 바꾼다.** 금관 상세를 선택하고, 상세를 읽었으므로 신규 `N` 표시를 확인 처리한다.
4. **표시 안내지를 새로 만든다.** 보여줄 페이지가 금관 상세이고, 금관의 신규 상태가 해제됐다는 값을 담는다.
5. **View가 안내지를 보고 화면을 그린다.** 금관 이름·그림·설명을 어디에 놓을지는 View가 결정한다.

중요한 구분은 **버튼을 눌렀다는 것과 그 행동이 허용된다는 것은 다르다**는 점이다. 기본 화면은 잠긴 유물 버튼을 비활성화하지만, 새 디자인에서 실수로 그 버튼을 활성화해도 Presenter가 복원 여부를 다시 검사해 상세 진입을 거절한다. 화면 교체가 수집 규칙을 우회하는 통로가 되지 않게 책임을 남겨 둔 것이다.

또한 그림을 다시 그리는 작업만으로는 신규 `N`이 지워지지 않는다. 실제로 상세를 여는 처리를 Presenter가 수행했을 때 원본 기록에서 확인 처리한다. 배경 이미지를 바꿨다는 이유로 사용자 기록이 바뀌면 안 되기 때문이다.

## 왜 원본 장부 대신 복사한 안내지를 줄까?

View의 일은 화면 표시다. 그런데 원본 기록의 변경 기능까지 View가 들고 있으면, 디자인을 만드는 코드에서도 복원 등록이나 신규 확인을 처리할 수 있게 된다. 그렇게 되면 화면 구현마다 게임 상태를 바꾸는 위치가 달라질 수 있다.

그래서 View에는 표시할 판정과 수치만 전달한다. 예를 들어 다음처럼 동작한다.

- 오전에 만든 안내지가 “복원 5종”이라면, 안내지를 읽는 동안 그 수치가 저절로 6으로 바뀌지 않는다.
- 실제 장부에 새 복원이 등록되면 변경 알림이 온다.
- Presenter가 최신 장부에서 “복원 6종” 안내지를 새로 만들고 View에 전달한다.

이렇게 하면 한 번의 화면 갱신 안에서 같은 기준의 수치와 판정을 사용한다. 이 안내지를 흔히 **스냅샷**이라고 부른다. 여기서는 “그 시점의 상태를 찍어 둔 복사본”이라는 뜻이다.

단, 그림·설명 자산까지 모두 복제한 것은 아니다. `Catalog`와 `Appearance`는 원래 자산을 함께 가리킨다. 따라서 “안내지를 받았으니 자산을 마음대로 수정해도 된다”는 뜻은 아니며, 표시 코드에서는 이 자산들을 읽는 용도로 사용한다. 이 안내지는 세이브 파일이나 서버 전송 형식도 아니다.

## 디자인을 바꿀 때 어디를 수정하면 될까?

| 바꾸려는 것 | 주로 수정할 곳 | Presenter의 수집·탐색 로직 |
| --- | --- | --- |
| 금관 그림이나 시대 대표 그림 | `CollectionCatalog.asset`의 그림 슬롯 | 유지 |
| 공통 배경·카드 바탕·아이콘 그림 | `CollectionAppearance.asset` | 유지 |
| 현 디자인의 카드 크기·간격·색상·배치 | `CollectionDefaultView` | 유지 |
| 도감 전체를 다른 레이아웃으로 교체 | 새 `CollectionView` 구현과 새 프리팹·View 연결 | 같은 페이지·규칙을 쓴다면 유지 |
| 복원 인정 시점·건물 해금 규칙 | 수집 모델과 해당 기능 연결 계층 | 기능 변경 범위에 따라 수정 필요 |
| 새로운 화면 종류나 새로운 사용자 행동 | View 계약·Presenter와 해당 기능 | 수정 필요 |

예를 들어 시대 카드를 세로 목록에서 가로 카드 형태로 바꾸더라도 “삼국을 누르면 삼국 상세를 연다”는 요청의 의미가 같으면 Presenter를 그대로 쓸 수 있다. 다만 새 레이아웃의 스크롤·탭 스와이프 입력 충돌은 새 View에서 기존 입력 계약에 맞춰 처리하고 검증해야 한다. **로직을 유지할 수 있다는 말이 입력 검증까지 생략해도 된다는 뜻은 아니다.**

현재는 기존 화면이 코드로 생성되므로, 크기·배치 변경도 기본 View 코드에서 작업한다. 이번 개편으로 이미 완성된 화면 프리팹이 생기거나, Inspector만으로 모든 배치를 바꿀 수 있게 된 것은 아니다. 바뀐 것은 **디자인을 고칠 코드와 게임 기능을 고칠 코드의 경계**다.

## 자주 나오는 용어

| 용어 | 여기서의 쉬운 뜻 |
| --- | --- |
| 컴포넌트 | Unity 오브젝트에 붙이는 역할별 부품. 글자 표시, 버튼, 렌더러, 동작 스크립트 등이 해당한다. |
| View | 사용자에게 보이는 화면을 만들고 입력을 알리는 코드. |
| Presenter | 입력을 검사하고 화면에 전달할 내용을 정리하는 코드. |
| 계약 | 서로 연결할 때 지켜야 하는 공통 사용법. 여기서는 `Initialize`, `Render`, 입력 요청의 의미를 말한다. |
| 이벤트 | “이 일이 생겼다”거나 “이 행동을 원한다”고 알리는 신호. 함수 호출을 연결해 응답하게 한다. |
| 바인딩 | 받은 데이터의 이름·그림·상태를 화면의 텍스트·이미지·버튼에 연결하는 일. |
| 프리팹 | 버튼·그림·텍스트와 배치를 묶어서 저장해 두는 재사용 가능한 Unity 오브젝트 틀. |
| 씬 인스턴스 | 프리팹 같은 틀을 실제 씬에 배치한 오브젝트. 틀 자체와 실행할 실물은 다르다. |
| 스크롤 정규화 위치 | 콘텐츠 길이와 관계없이 맨 위를 1, 맨 아래를 0으로 나타낸 위치. |
| 레이어 | 어떤 탭 카메라가 어떤 오브젝트를 볼지 구분하는 묶음. 여기서는 탭끼리 그림이 섞이지 않게 사용한다. |

## 이전 CanvasRenderer 오류와는 어떤 관계일까?

이전 오류 수정은 **임시 그림을 출력하는 데 필요한 부품을 빠뜨리지 않게 한 것**이다. 이번 개편은 **그림·배치를 담당하는 코드와 기능을 담당하는 코드를 나눈 것**이다. 서로 다른 작업이며 둘 다 유지된다.

그림 파일이 없으면 기본 View는 `CollectionArtwork`라는 임시 기호를 만든다. 이 기호는 모양을 구성하고, `CanvasRenderer`는 UI 출력에 필요한 부품이다. `CollectionArtwork`에 선언한 `RequireComponent`가 새 기호를 만들 때 렌더러도 함께 붙이게 한다. 따라서 View가 그림을 생성할 때마다 같은 보완 코드를 반복할 필요가 없다.

새 디자인이 그 임시 기호를 계속 쓰면 같은 필수 부품 보장을 받는다. 임시 기호를 없애고 기본 `Image`로 실제 그림만 표시한다면 해당 표현으로 교체하면 된다. 이 변화 때문에 수집률이나 잠금 판정까지 고칠 필요는 없다. [오류 및 수정 보고서](collection-error-reproduction.md)에 재현과 수정 검증을 기록했다.

## 이번에 분리한 책임

기존 `CollectionPresenter`는 수집 기록 구독·잠금 검사·화면 이동과 UI 오브젝트 생성·좌표·색상·그림 선택을 함께 담당했다. 디자인 변경 때 기능 코드까지 수정해야 하는 범위를 줄이기 위해 다음과 같이 나눴다.

| 코드 | 담당 |
| --- | --- |
| `CollectionPresenter` | 진행 기록 구독·교체, 선택 ID와 현재 페이지, 잠긴 유물 접근 거절, 열람 처리, 페이지별 스크롤 기억 |
| `CollectionViewData` | 화면 갱신 시점의 복원·신규·건물 해금 판정과 통계 복사본, 선택 페이지·ID와 고정 표시 자산 참조 |
| `CollectionView` | 교체할 표시 구현의 계약. 초기화·데이터 적용과 시대/유물/뒤로가기 입력 의도 전달 |
| `CollectionDefaultView` | 기존 UI의 생성·배치·색상·그림 대체 우선순위·버튼·스크롤·메시 구성 |

View는 `CollectionProgress`를 보관하거나 복원 완료·열람 처리를 호출하지 않는다. 버튼은 ID를 포함한 입력 의도만 알리고 Presenter가 유효성·잠금을 검사한 뒤 상태를 바꾼다. 예를 들어 새로운 디자인이 잠긴 유물 선택을 잘못 전달하더라도 Presenter의 `ShowRelic` 검사가 상세 진입을 거절한다.

복원·신규·해금 판정은 기존 도메인 모델에서 계산한 값을 복사한다. 표시 도중 원본 기록이 바뀌어도 이미 전달한 복사본의 판정은 변하지 않으며 다음 갱신에서 새 복사본을 전달한다. 카탈로그·Appearance의 그림과 설명은 기존 ScriptableObject 참조를 공유하므로 이 데이터 전체를 자산까지 깊게 복제한 불변 저장 포맷으로 해석하지 않는다.

## 기존 씬의 실행

씬의 Presenter 필드 `_catalog`, `_font`, `_appearance`와 기존 공개 화면 이동 API는 유지했다. 기존 씬의 GUID와 연결을 바꾸지 않았다.

1. Presenter에 `_view`가 연결돼 있으면 그 인스턴스를 사용한다.
2. 연결이 없으면 같은 계층의 `CollectionView`를 찾는다.
3. View가 없으면 `CollectionDefaultView`를 런타임에 추가한다.

따라서 기존 `Collection.unity`는 이관 명령이나 씬 재생성 없이 기본 디자인으로 실행된다. `Scroll`, `BackButton`, `EraButtons`, `RelicButtons`, `StatsText`, `BuildingStatusText`는 기존 통합 검증과 호출부를 위해 View에서 전달한다. Presenter에는 카드 좌표나 색상 상수를 남기지 않았다.

탭을 숨기거나 다시 보일 때는 기록 알림 연결을 끊었다가 다시 연결한다. 숨긴 동안 바뀐 기록은 다시 보일 때 갱신한다. 반면 View의 버튼 요청 연결은 두 객체가 살아 있는 동안 유지하고 Presenter가 파괴될 때 해제한다. 이 두 연결의 수명이 다른 이유는 하나는 “기록이 바뀌었다”는 구독이고 다른 하나는 “이 화면의 버튼을 어느 담당자에게 보낼지”라는 연결이기 때문이다.

기록이 같은 프레임에 여러 번 바뀌면 바로 여러 번 다시 그리지 않고 갱신을 예약해 모아서 처리한다. `LateUpdate`는 Unity가 매 프레임 뒤쪽에서 호출하는 함수로, 여기서 최신 안내지 한 장을 만들어 전달한다. 유물 상세를 여는 것처럼 즉시 표시하는 경로에서는 이미 처리한 갱신을 다시 반복하지 않도록 예약을 정리한다.

## 새로운 디자인을 연결하는 방법

1. `CollectionView`를 상속하는 새 표시 컴포넌트를 만든다. 새 프리팹의 텍스트·버튼·이미지 참조와 배치는 그 컴포넌트에서 관리한다.
2. `Initialize(root, font)`에서 `MirrorSceneRoot`의 콘텐츠 카메라, 레이어와 UI 입력 경계를 따른다. 전용 EventSystem이나 AudioListener를 만들지 않는다.
3. `Render(data, scrollPosition)`에서 표시 데이터를 연결한다. 기록을 새로 만들거나 복원 완료·신규 확인을 처리하지 않는다.
4. 버튼은 `RequestEra(id)`, `RequestRelic(id)`, `RequestBack()`을 호출하도록 연결한다.
5. 새 View를 가진 프리팹의 **씬 인스턴스**를 Presenter 아래에 두고 `_view`에 연결한다. Project 창의 프리팹 자산 자체를 런타임 인스턴스 대신 연결하지 않는다.
6. 기본 입력 호환성을 유지하려면 `CollectionScrollRect`와 공통 MirrorInput 경로를 사용한다. 스크롤이 없는 디자인은 기본 `ScrollPosition=1`을 사용할 수 있고, 다른 스크롤 표현이면 해당 속성을 재정의한다.

이 경계 안에서 카드 크기·색상·배치·그림과 화면 레이아웃을 바꿀 때 Presenter의 수집·탐색 로직은 그대로 사용할 수 있다. 신규 페이지나 게임 규칙 자체가 바뀌면 계약과 Presenter도 별도 변경해야 한다.

## 첫 단계의 범위와 남은 작업

이번에는 현재 코드로 생성하던 화면을 기본 View로 옮기고 교체 경계를 만들었다. 실제 새 디자인, 카드별 프리팹, Inspector에서 배치 가능한 완성형 화면 프리팹은 아직 제작하지 않았다. 기본 View 내부에는 기존 좌표와 색상이 남아 있으며, 현 디자인을 고칠 때는 해당 View를 수정한다. 코드 없이 모든 디자인을 교체할 수 있는 상태는 아니다.

후속 작업은 확정 디자인에 맞춰 시대 카드·유물 카드·상세 패널 프리팹을 만들고, 새 View에서 표시 데이터를 바인딩하는 것이다. 런타임 View 교체·전환 애니메이션·화면 캐싱 정책은 이번 범위에 포함하지 않았다.

## 코드를 읽는 추천 순서

1. [CollectionView.cs](../Assets/MobileUI/Scripts/Collection/CollectionView.cs): 화면 담당자와 처리 담당자 사이의 사용법부터 읽는다. `RequestRelic`은 요청이고 `Render`는 처리 결과를 받아 표시하는 함수다.
2. [CollectionPresenter.cs](../Assets/MobileUI/Scripts/Collection/CollectionPresenter.cs): `Awake`에서 연결하는 순서와 `ShowRelic`에서 잠금을 검사하고 신규 표시를 확인하는 순서를 본다.
3. [CollectionViewData.cs](../Assets/MobileUI/Scripts/Collection/CollectionViewData.cs): 원본 기록을 보관하지 않고 표시할 값만 복사하는 부분을 본다.
4. [CollectionDefaultView.cs](../Assets/MobileUI/Scripts/Collection/CollectionDefaultView.cs): `Initialize`가 공통 틀을 만들고 `Render`가 현재 페이지를 표시하는 흐름을 본다. 좌표·색상 코드는 기능 규칙과 분리돼 있다.

개발 시에는 “이 코드는 장부를 바꾸는 일인가, 무엇을 보여줄지 정하는 일인가, 어떤 모양으로 보여줄지 정하는 일인가?”로 먼저 구분하면 수정할 위치를 고르기 쉽다.

## 검증

- `CollectionViewDataTests`: 복원·열람 상태가 바뀌어도 이전 표시 데이터가 유지되는지, 복사본 생성이 신규 기록을 확인 처리하지 않는지, 기존 해금·통계 판정과 일치하는지 검사한다.
- `CollectionViewContractTests`: 실제 UI를 생성하지 않는 대체 View를 주입해 기본 View가 중복 생성되지 않고, 잠금 검사·열람 처리·뒤로 가기·스크롤 없는 디자인의 기록·외형 갱신이 Presenter를 통해 동작하는지 검사한다. 대체 컴포넌트는 `Tests/Support`의 테스트 전용 어셈블리에 두며 일반 Player에는 포함하지 않는다.
- 기존 EditMode 검사와 실제 Windows Player 통합 검증 결과는 [도감 검증 기록](collection-validation.md)에 기록한다.
- 도감의 수집 규칙·작업대 연결 계약은 [도감 연결 계약](collection-integration.md)을 유지한다.

2026-10-28 실행 결과: Unity 6000.3.23f1에서 EditMode **203개 통과, 실패 0개, 기존 외부 서버 연동 검사 3개 건너뜀**. Windows Development Player 빌드 성공, Player 자동 검사 **227개 통과**. 최종 로그의 MissingComponentException·런타임 예외·지정 GPU 종료 오류 패턴은 0건이다. 시대 목록·유물 상세 등의 캡처도 확인했다. 실제 Android/iOS 터치·성능은 검증하지 않았다.

첫 Player 실행은 도감 검사를 통과한 뒤 작업대 재시작의 도구 수 기대값 `30` 때문에 중단됐다. 현재 Normal 보드의 초기 도구 수는 19이므로, `IntegratedVerification`의 재시작 검사 두 곳을 현재 실행의 초기 횟수와 비교하도록 수정했다. 새 세션 생성·횟수 복원·중복 타일 부재 검사 자체는 유지했으며 게임 규칙이나 난이도 값은 변경하지 않았다. 이후 다시 빌드하고 전체 227개 검사를 통과했다.

이번 실행 증거(로그·빌드는 Git 제외):

- `Logs/Integration/collection-refactor-editmode.xml`, `collection-refactor-editmode.log`.
- `Logs/Integration/collection-refactor-build-final.log`: `INTEGRATED_BUILD_SUCCESS`, Editor 종료 코드 0.
- `Logs/Integration/Player-CollectionRefactorFinal-20261028-192355/verification.txt`, `player.log`, 도감 PNG 캡처.

`VerifyIntegration.ps1`은 이번 NUnit 전체 결과의 `Skipped:Ignored`를 성공으로 인정하지 않으므로 EditMode·빌드·Player 단계를 각각 실행하고 결과를 확인했다. 건너뛴 3개를 통과로 합산하지 않았다. 빌드 중 Unity가 자동 갱신한 렌더링·프로젝트 설정 파일은 원래 상태로 되돌렸으며 이 개편에 포함하지 않았다.
